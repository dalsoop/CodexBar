# 로컬 관리와 비밀값

| 주체와 조건 | 허용 | 거절 |
| --- | --- | --- |
| status의 hub·standalone, 실행 중 로컬 서버 | 명시적 키 관리와 검증된 대시보드 열기 | 다른 Mac의 관리 자격 배포 |
| client | 허브에서 관리하라는 안내 | 네이티브 키 조회·변경·내장 관리 창 |
| 역할 불명·손상된 응답·서버 중지 | 고정 오류와 사용자 새로고침 | 추정 권한과 자동 복구 변경 |
| 생성 결과를 보고 있는 사용자 | 새 키 표시와 명시적 복사 | 기존 키 비밀값 재조회 |

변경 직전에 역할을 다시 확인한다. Opencodex의 기존 로컬 클라이언트가 관리 인증을 담당한다. CodexBar는 관리 토큰·설정 파일·OAuth 자격을 수집하거나 새 설정에 저장하지 않는다. 인증 거절·통신 실패·형식 오류의 원시 응답은 사용자 오류문과 로그로 전달하지 않는다.

이름 변경 보조 실행기는 지원하는 Opencodex 설치에만 연결하고 고정 ID PATCH 한 번만 수행한다. 입력으로 주소·HTTP method·path·인증값을 받지 않는다. 리다이렉트를 거절하며 출력은 검증된 메타데이터나 고정 오류 코드로 제한한다. 인증값은 기존 Opencodex 프로세스 안에 머문다.

생성 비밀값은 일반 목록·Codable 저장 모델·디버그 설명에서 분리한다. 결과 화면을 닫거나 앱이 종료되면 보관 참조를 해제한다. 메모리의 모든 물리적 사본을 덮어쓴다고 주장하지 않는다. 복사는 사용자 동작에만 반응하며 기기 내·비밀·일시 pasteboard 항목으로 기록한다. 기본 60초 뒤 자신의 항목이 그대로인 경우에만 삭제한다. 사용자가 나중에 복사한 내용은 삭제하지 않는다.

대시보드 URL은 자격 없는 HTTP(S)와 유효한 호스트만 허용한다. HTTP는 정확한 localhost·127.0.0.1·::1만 허용하고 나머지 호스트는 HTTPS를 요구한다. TLS 오류를 우회하지 않는다. 같은 origin은 내장 창에 유지한다. 다른 origin의 탐색은 링크·새 창·스크립트 여부와 관계없이 취소하며 웹 탐색 콜백에서 외부 앱을 실행하지 않는다. 최상위·새 창 요청은 주소를 보류하고 고정 안내와 CodexBar의 브라우저 열기 버튼을 제공한다. 외부 하위 프레임은 브라우저 호출이나 보류 주소 변경 없이 차단한다. 외부 브라우저 호출은 유효한 관리 상태와 안전한 보류 주소를 다시 확인한 네이티브 버튼 동작에만 허용한다. WebKit의 링크 분류나 새 창 대상 부재를 실제 사용자 입력의 증거로 쓰지 않는다.

웹 인증은 기존 대시보드에서 사용자가 직접 한다. 전용 비영구 WebKit 저장소는 열린 창 안에서만 유지하고 닫으면 WebView와 세션을 해제한다. 다른 앱의 쿠키 가져오기·인증 자동 클릭·JavaScript 비밀 브리지는 추가하지 않는다. 웹 요청·HTML·쿠키·관리 응답을 자동 수집하지 않는다.

검증은 가짜 CLI·메모리 설정·합성 홈·가짜 클립보드를 사용한다. 실제 SecItem 조회, 실계정 probe, 브라우저 쿠키 가져오기는 사용자의 명시적 요청이 필요하다. 쿠키 기능을 수정할 때는 공통 BrowserCookieAccessGate의 백그라운드 차단·호스트 일치·수동 동작당 최대 한 번의 대화형 Keychain 읽기·거절 대기시간을 유지한다. 수동 CLI의 명시적 allow-keychain-prompt 외에는 이를 우회하지 않는다.

운영 기록에는 비밀값 없는 변경 종류·성공 여부만 남길 수 있다. 비밀값·사용자가 입력한 이름·실행 인수·원시 stdout/stderr·웹 본문을 기록하지 않는다. 개발 증거는 합성 자료만 쓰며 실제 키 발급·소비·폐기로 테스트를 증명하지 않는다.

Linux 표시 backend는 사용자 소유 runtime 디렉터리와 같은 사용자 소켓을 사용한다. 디렉터리 소유자 불일치나 symlink를 허용하여 다른 사용자에게 IPC를 열지 않는다. 어댑터 snapshot에는 계정 신원·CLI 경로·자격 설정을 넣지 않는다. 공급자 인증은 설치된 CLI에서 처리하고 터미널 로그인 출력을 데스크톱이 수집하지 않는다.

CodexBar의 기존 HTTP server는 Opencodex 관리 서버와 별개다. 기본 loopback의 조회 경로가 열려 있다는 사실을 네트워크 바인딩에 적용하지 않는다. 비-loopback에서는 데이터 경로 bearer 인증과 평문 HTTP 전송의 명시적 수락을 요구한다. token이 있다는 이유로 TLS를 제공한다고 표시하거나 Opencodex 자격으로 재사용하지 않는다.
