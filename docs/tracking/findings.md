# 미해결 문제

전체 PreferencesView를 표시 순서에 올리지 않은 NSWindow에서 cacheDisplay로 촬영하면 위쪽 제목이 잘리고 선택한 sidebar 행의 문자·재질이 누락된다. 같은 기능을 별도 pane으로 호스팅하면 한국어 내용과 동작 버튼은 정상이며 검사도 통과한다. 이 현상만으로 운영 앱의 표시 결함이라고 판단할 수 없다.

영향은 전체 설정 창의 시각적 검증에 한정된다. 모델·선택 경로·창 재사용·비밀값 해제와 별도 pane의 내용 검증을 대신 실패로 보지는 않지만, 이를 전체 앱 시작 검증으로 확대하지 않는다. 기본 앱 시작이 실제 설정·계정 초기화를 포함하므로 현재 검증에서는 실행하지 않았다. 운영 상태를 침범하지 않는 전체 앱 fixture 진입점이나 별도 macOS 환경을 확보한 뒤 실제 창 구성을 다시 확인할 수 있다.

설치된 메뉴 막대 전용 앱은 현재 화면 제어 도구의 앱 목록에 나타나지 않고 직접 선택도 timeout으로 끝난다. 원인 조사에서 설치본의 `LSUIElement=true`와 Launch Services의 `UIElement` 분류를 확인했다. `DockIconController`는 설정을 열 때만 `.regular`로 전환하며 창이 사라지면 `.accessory`로 복귀한다. 앱은 untitled 창 열기를 거절하고 별도 `applicationShouldHandleReopen` 처리를 제공하지 않으므로 앱을 다시 여는 동작만으로 설정 창을 얻을 수 없다.

도구 연결이 `native pipe closed before response`로 끊어지는 별도 문제도 발생했다. 화면 제어 세션을 초기화하자 Finder의 접근성 조회는 정상 복구됐지만, 같은 새 연결에서 설치본 전체 경로로 CodexBar를 선택하면 다시 약 5초 뒤 `-10005: timeoutReached`가 발생했다. 설치본은 계속 실행 중이며 2초 프로세스 표본의 주 스레드는 AppKit 이벤트 루프에서 대기했다. 이 표본에서는 주 스레드 정지 증거가 없었다. 따라서 메뉴 막대 전용 앱 선택 경로의 도구 호환 문제가 주된 가설이며, 도구 내부의 정확한 대기 조건은 확인하지 못했다. 일반 앱 접근이 복구된 상태이므로 시스템 접근성 권한 전체를 초기화하는 조치는 우선하지 않는다.

즉시 우회는 메뉴 막대에서 설정 창을 한 번 여는 것이다. 기존 코드가 일반 앱 모드로 전환하므로 창 기반 선택을 다시 시도할 수 있지만, 실제 창이 열린 상태의 도구 접근은 아직 미검증이다. 앱 쪽 개선 후보는 사용자가 실행 중인 앱을 다시 열 때 `applicationShouldHandleReopen`에서 기존 설정 창 컨트롤러를 호출하는 것이다. 자동 로그인 시작은 창 없이 유지하고, 재열기 시 기존 창을 재사용하며, 실제 Finder 재열기 이벤트와 도구 접근을 검증해야 한다. 도구가 같은 재열기 이벤트를 보내는지는 별도 확인이 필요하므로 이 변경만으로 CUA 문제가 해결된다고 단정하지 않는다. `LSUIElement` 제거·서명된 Info.plist 직접 수정·접근성 권한 초기화는 적용하지 않았다.

새 설치 프로세스의 실행·서명·실제 허브와 키 목록 해석·대시보드 HTTP 응답은 별도로 확인했지만, 이를 실제 설정 화면 검증으로 확대하지 않는다. 원인 조사 증거는 로컬 `.dryforge/install/ui-diagnosis.json`과 프로세스 표본에 보관한다.
